## Context

`DashboardView.tsx` 目前將四個欄寬百分比直接設為 flex item 的 CSS `width`，三條固定 6px 分隔線則額外占用空間，因此即使比例總和為 100%，實際總寬仍會超出容器。拖曳演算法也可能在相鄰欄位達最小值後繼續放大左欄，使比例總和失衡；`localStorage` 載入僅驗證陣列形狀與型別，既有異常值會持續套用。

## Goals / Non-Goals

**Goals:**

- 讓欄寬比例只分配扣除固定分隔線後的剩餘空間。
- 以單一、可測試的規則驗證欄寬，阻止拖曳與舊持久化資料造成溢出。
- 提供雙擊任一分隔線即可回復四欄平均寬度的復原操作。
- 保留目前即時拖曳與 `localStorage` 持久化體驗。

**Non-Goals:**

- 不依卡片文字內容計算個別欄位的最佳寬度。
- 不新增水平捲動、欄位收合、欄位排序或可設定的最小寬度。
- 不變更後端設定格式或加入新套件。

## Decisions

### 1. 將欄寬視為剩餘空間的權重

欄位改用 `flex-basis: 0` 搭配以比例為值的 `flex-grow`，分隔線維持固定寬度且不縮放。Flex 佈局會先扣除三條分隔線，再依四個權重分配剩餘空間，因此合法比例不會因固定像素分隔線而超出容器；視窗縮放時也會由瀏覽器自動重新配置，不需要額外的 resize listener。

替代方案是以 JavaScript 測量容器後為每欄計算像素寬度，但會增加 `ResizeObserver`、同步時序與像素捨入處理，對目前需求沒有必要。

### 2. 拖曳只重新分配相鄰兩欄

拖曳開始時保存比例快照；移動量以「容器寬度減去全部分隔線寬度」換算為比例。分隔線兩側欄位的比例總和固定，先依 10% 最小欄寬限制計算左側合法範圍，再以該總和推導右側比例。這可保證每次更新後四欄總和仍為 100%，不使用先放大再個別 clamp 的計算方式。

替代方案是讓單一欄位變寬並按比例壓縮右側所有欄位，但互動較難預期，也偏離現有「壓縮相鄰欄」規格。

### 3. 無效持久化資料直接回復平均值

抽出純函式驗證欄寬資料：必須是四個有限數值、每個至少 10%，且總和在浮點容許誤差內等於 100%。不符合時回傳 `[25, 25, 25, 25]`；合法資料可將極小浮點誤差正規化為 100%。存檔前也使用相同規則，避免再次寫入不可恢復狀態。

替代方案是嘗試修補任意異常比例，但分配剩餘比例的規則不具使用者意圖依據；直接回復平均值較可預測，也能確保失控版面立即復原。

### 4. 雙擊分隔線重設整個看板

每條分隔線處理 `dblclick`，統一將欄寬 state 設為平均值。既有持久化 effect 會儲存新值，因此不增加另一條儲存路徑。雙擊調整全部欄位而非只調整相鄰欄，符合「自動調整整體寬度」並提供明確的全域復原操作。

## Risks / Trade-offs

- [極窄視窗下 10% 欄位仍可能不足以閱讀內容] → 欄內既有截斷與 `overflow: hidden` 繼續保護版面；本變更只保證看板外框不溢出。
- [單擊拖曳與雙擊事件可能在短暫移動時互相影響] → 雙擊直接覆寫最終 state，並在事件處理中避免瀏覽器文字選取；以互動測試覆蓋拖曳後雙擊結果。
- [舊的合法但使用者不喜歡的比例仍會保留] → 這是既有持久化預期；使用者可雙擊任一分隔線主動恢復平均值。

## Migration Plan

不需資料遷移。新版首次載入看板時會驗證現有 `localStorage` 值，異常值自動回復並由既有持久化流程覆寫。若需回滾，舊版仍可讀取四元素數字陣列；平均值完全相容。
