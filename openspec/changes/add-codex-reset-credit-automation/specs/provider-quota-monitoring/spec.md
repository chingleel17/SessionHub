## MODIFIED Requirements

### Requirement: 可於 App 內消耗 Codex 手動重置額度

QuotaOverview 的 Codex 重置額度標題前 SHALL 顯示使用重置按鈕，僅在 snapshot 有 `reset_credits` 時出現。可用次數為 0、操作進行中或快照尚無可驗證的目前帳號身分時 SHALL 停用按鈕。按下按鈕 SHALL 先經應用程式共用確認對話框二次確認，不得單次點擊即送出消耗請求；Tauri IPC 由 App 元件發起。手動與自動使用 SHALL 共用同一帳號的消耗協調與結果刷新；自動使用依獨立設定授權，不套用此手動按鈕的逐次確認。

#### Scenario: 確認後使用一筆重置額度

- **WHEN** 使用者確認操作，且 Codex 額度監控已啟用、具有 ChatGPT 帳戶 ID 與可用重置額度
- **THEN** 後端先重新查詢可用重置額度，再以相同 Codex 憑證呼叫 `POST https://chatgpt.com/backend-api/wham/rate-limit-reset-credits/consume`
- **AND** 請求 JSON 包含新產生的 `redeem_request_id`，若有 account ID 則附帶 `ChatGPT-Account-Id` header
- **AND** 前端顯示後端回傳的 `reset`、`nothing_to_reset`、`no_credit` 或 `already_redeemed` 對應結果，完成後重新整理 Codex 額度與可用次數
- **AND** 取得帳號執行權後仍須重新驗證帳號與可用額度，不得因等待期間登入帳號改變而消耗另一帳號
- **AND** 開啟確認視窗時綁定所見快照的帳號範圍，確認送出時攜帶該範圍；後端須與目前解析出的帳號一致才接受操作

#### Scenario: 取消確認或額度不可用

- **WHEN** 使用者取消確認，或可用重置額度為 0
- **THEN** 不送出消耗請求

#### Scenario: 重置請求失敗或結果不明

- **WHEN** 憑證無效、請求失敗、回應格式未知或網路逾時
- **THEN** 顯示錯誤或提示使用者重新整理確認結果
- **AND** 操作按鈕恢復可用狀態，並重新整理 Codex snapshot；不得自行宣稱已完成重置
- **AND** 結果不明尚未解除時，後端不得接受同一帳號任何新消耗；按鈕可回報需重新整理確認的狀態。僅在重新查詢確認原觀察券皆不可用，或其到期時間皆已過且沒有未知到期券時解除

#### Scenario: 自動使用進行中遇到手動使用

- **WHEN** 同一帳號已有自動消耗請求，使用者同時確認手動使用
- **THEN** 不並行送出第二筆消耗，回報處理中或等待既有請求完成
- **AND** 等待後若仍要執行，重新查詢並確認有可用券；已無可用券則不送出

#### Scenario: 僅有 OpenCode 的 OpenAI 登入可供查詢

- **WHEN** 目前 Codex 用量查詢採用既有 OpenCode OpenAI OAuth 備援來源
- **THEN** 手動與自動消耗皆使用相同憑證解析結果及同一 ChatGPT 帳號
- **AND** 無法取得可驗證的 ChatGPT 帳戶 ID 時拒絕消耗，顯示需登入的原因，不改用另一帳號的 Codex CLI 憑證

#### Scenario: 確認對話框開啟後切換帳號

- **WHEN** 使用者根據帳號 A 的快照開啟確認視窗，在確認前登入來源已切成 B
- **THEN** 本次操作取消並提示帳號已變更，重新整理目前帳號資料
- **AND** 不向 A 或 B 送出本次消耗，不以 B 的資料靜默取代原確認內容

#### Scenario: 啟動載入未綁定帳號的舊快照

- **WHEN** 啟動時顯示持久快取的 Codex 用量，但尚未確認快照屬於目前登入帳號
- **THEN** 快取可繼續唯讀顯示，使用重置按鈕停用
- **AND** 成功取得目前帳號的最新快照後才允許開啟消耗確認

#### Scenario: 可用張數與可確認明細不一致

- **WHEN** 手動操作重新查詢得到正的可用數，但無法以 active 明細確認相同張數
- **THEN** 不送出消耗，顯示資料不一致並要求重新整理
- **AND** 未知狀態或缺漏明細不得成為繞過結果不明阻擋的依據

## ADDED Requirements

### Requirement: Codex 用量結果須維持目前帳號的一致性

Codex 快照、手動確認及自動化狀態 SHALL 具有可核對的帳號範圍。帳號切換後，舊帳號延遲完成的查詢或消耗結果 SHALL 不得覆寫目前帳號的可操作資料；其執行結果仍記入原帳號歷史。載入的舊快取在確認帳號前 SHALL 不得授權消耗，帳號不一致的結果亦不得透過更新事件重新呈現為目前帳號資料。

#### Scenario: 帳號 A 的查詢晚於 B 完成

- **WHEN** A 的查詢尚未完成時已切換 B，B 的最新資料已顯示，之後 A 的回應才到達
- **THEN** 目前可操作的 Codex 快照與自動化狀態維持 B
- **AND** A 的延遲回應不覆寫 B 的記憶體快取或持久快照，也不讓前端透過事件重新載入 A 的資料

#### Scenario: 帳號切換前已送出消耗

- **WHEN** A 的消耗已進入送出階段，切換 B 後才收到 A 的結果
- **THEN** 結果記入 A 的請求歷史，不宣稱能撤回已送出的操作
- **AND** B 的狀態及用量不被 A 的結果刷新覆寫
