# Design

## Context

動機見 `proposal.md`。目前資料與限制如下：

- `src-tauri/src/types/quota.rs` 的 `ResetCredits` 提供總可用張數與明細；每筆僅有 `granted_at`、`expires_at`、`status`，沒有穩定券 ID。到期時間可缺少，既有轉換精度為 UTC 秒。
- `quota/codex.rs` 已有 GET reset-credits 與 POST consume。POST 僅接受 `redeem_request_id`，不能指定券；目前沒有服務端最早到期優先或重試冪等性的已驗證契約。
- 查詢可退回 OpenCode 的 OpenAI OAuth，但現有消耗僅讀 Codex CLI 憑證，需讓查詢／消耗使用同一個解析結果。
- `app_setup.rs` 現有背景用量刷新每 60 秒檢查、約每 30 分鐘刷新，不足以處理一分鐘的到期區間。
- 設定由 `AppSettings` 持久化；原生通知已有 Tauri plugin。前端 IPC 集中 `App.tsx`，通知與消耗不能依賴前端頁面保持掛載。

## Goals / Non-Goals

**Goals:**

- 將時間判斷與副作用分離，可用假時鐘、假 API 與假通知驗證邊界。
- 對同一帳號的一次消耗使用同一組已解析憑證，並在手動／自動、重啟及併發之間協調。
- 以小型背景協調器及既有 SQLite／通知能力完成，避免建立通用排程系統。

**Non-Goals:**

- 不建立逐券 ID、不模擬使用者產生 Codex 用量來耗完券、不猜測服務端選券順序。
- 不新增跨多帳號管理、雲端排程、OS 常駐服務或退出後執行機制。

## Decisions

### 1. 固定自動使用提前量，提醒使用日曆天

設定欄位與預設值以 `specs/app-settings/spec.md` 為準：兩個開關預設關閉，每日 `09:00`，提前 `0–30` 天。自動使用固定 `60` 秒，以具名常數表示，不增加另一個提前量欄位。

- 提醒採本地日曆日期，區間為 `(now, start_of_local_day(today + days_before + 1))`；「今天」及「未來 D 天」分別計數。跨日計算使用日期／時區轉換，不用 `24h * 天數` 代替，處理日光節約時間。
- 自動使用以 UTC 時刻比較，區間為 `[expires_at - 60s, expires_at)`，恰好到期不送新請求。
- 未知 status 不推定可用；`active` 且缺到期時間可繼續顯示，但不排程。自動使用前核對總可用張數與 active 明細數；不一致即暫停。
- 前後端均驗證 `HH:mm` 與整數天數；載入時使用逐欄位容錯／正規化，避免負數或錯誤型別使整份設定載入失敗。儲存時拒絕無效輸入，不把錯誤資料靜默存成預設值。
- 前端 `mergeAppSettings` 只保留 `DEFAULT_APP_SETTINGS` 既有鍵，因此四個新欄位必須同步加入 `src/utils/appSettingsDefaults.ts`；驗證須包含真正經過表單合併的儲存往返，不僅是 Rust／JSON 序列化。
- 釘選或其他功能的背景保存須沿用目前已儲存的四個重置券值，不能把設定頁草稿一起送出；只有明確按下設定儲存時才採用草稿。
- `save_settings` 以選填 `updateResetCreditSettings` 區分明確儲存（true）與背景保存（缺省／false）；後端在同一設定閘門內合併目前四個值，避免並行保存使用過期的前端快照覆寫剛生效的開關。

**取捨：** 以「每日時間＋提前天數」滿足需求，避免任意 cron、逐券時間及小時／分鐘提醒組合造成設定複雜化。

### 2. Rust 背景協調器處理到期工作

新增 `quota/reset_credit_automation.rs`，由 `app_setup.rs` 啟動一個可被事件喚醒的背景協調器。狀態由後端持有；command 為薄包裝，協調器不依賴 `commands/` 或 React。

觸發來源：

1. 啟動、相關設定儲存、憑證／帳號變更、既有 Codex 快照更新。
2. 最長每 10 秒檢查牆上時鐘、設定版本與到期工作；喚醒後的第一輪自然重算，無需以專用喚醒事件作為唯一依據。
3. 自動使用有效時，正常情況下每 5 分鐘補查一次目前帳號的重置券，用於發現新券／手動兌換；不對所有 provider 執行高頻刷新，服務端退避或已知失效憑證可延後／暫停查詢。
4. 每日提醒與實際消耗前，再執行不使用舊快取的查詢。一般快照只用於發現候選工作，不授權副作用。

以最早下一工作時間與 10 秒上限決定等待時間；網路工作在背景執行，不阻塞 UI 或其他 provider 刷新。每帳號查詢合併，避免提醒、五分鐘更新與到期事件同時觸發重複查詢。一般刷新可協助發現候選，但不得消耗提醒的重試名額或繞過同一 reset-credits 端點的服務端退避。提醒取得執行權後的查詢才計入當日最多三次；等待現有查詢的多個觸發者不能各自再送一次。

設定儲存與送出執行權的核發共用短時間的設定版本閘門：關閉設定先完成則不再授予舊版本新執行權；已取得執行權並寫入 pending 的請求視為已開始送出。此閘門不持有到網路回應完成，且儲存成功回應前已發布新的設定版本。尚未進入此階段的取消不建立消耗終止紀錄；再次開啟時可根據新設定建立新待辦。已開始送出的批次及結果不明的日誌不因重新開啟而清除。

重置券四個設定或 Codex／OpenCode 來源根目錄變更時遞增程序內世代，不只比較最終設定值；關閉後立刻重開成相同值，也不能復活舊 GET 對應的工作。平台監控、釘選及視窗設定等無關變更不影響此世代或憑證 revision。世代在查詢開始時捕捉，不能在回應結束後才補上最新世代。核發送出權時，在閘門內取得並核對真正要使用的憑證 context，再寫 pending；核發後沿用該 context，不因後續儲存或切帳號重新解析／拒絕已核發操作。實際開始 HTTP 前仍檢查到期時間，避免資料庫等待或喚醒造成逾期送出。

原生提醒在保留通知提交紀錄前，同樣以短時間閘門核對提醒開關、目前帳號、設定版本及當日範圍；已認領後設定改變造成取消時，保留本次已檢查紀錄，不重新產生當日第二次提醒檢查。不得在停用已生效後才依舊工作授予新的通知提交權。

通知提交權保留後立即釋放設定閘門，再呼叫原生通知插件，避免通知或 UI 執行緒等待延長設定儲存的鎖定時間。

GET 的暫時性失敗可有界重試：每日檢查最多 3 次，首次失敗後分別等待 30 秒、120 秒；到期前查詢最多 3 次，失敗後分別等待 10 秒、20 秒，且每次重試都不得超出到期區間。尊重服務端較長的退避要求，若將超過期限則停止。單筆 HTTP 呼叫設定不超過 10 秒的逾時，POST 無自動重送。

每日次數與下次允許時間在查詢前持久化，GET 進行中崩潰也視為已使用一次名額；重啟不重設。自動批次的 GET 次數與下次允許時間亦持久化，避免每個 tick／重啟重新獲得三次機會。跨本地日期即取消舊日提醒重試；端點的服務端退避仍沿用剩餘時間。認證失敗及格式不合法不列為暫時性失敗，不在同一工作內重試。

既有 quota refresh 會持有 DB mutex 進行網路查詢，不能僅在新協調器中避免鎖定。需限縮調整相關刷新呼叫鏈，改為先擷取設定／帳號 context、釋放 DB 鎖查詢，再以短交易提交快照；不改變其他 provider 的查詢規則。以慢速假 provider 驗證其請求進行時，重置券協調仍可讀寫日誌及檢查期限。

**取捨：** 延續程序內背景執行，不使用前端 `setInterval`，也不新增工作排程器。正常喚醒的檢查精度為十秒等級，不保證作業系統負載、休眠或網路延遲下的準點成功。

### 3. 共用帳號解析與消耗協調

將現有憑證解析整理為 quota 內部的 account context，包含憑證來源、ChatGPT 帳號 ID 及僅在記憶體使用的授權資料。GET 與 POST 接收同一 context，保留既有 Codex 優先、OpenCode 備援來源；不得查到 A 的券後重新解析並送往 B。

自動化直接查詢回傳有型別的結果：`available`（含合法的零張）、`unsupported`（如 404）、`no_auth`、`transient_error`、`invalid_response`。不得把 adapter 的 best-effort `reset_credits: null` 視為零張；缺少必要計數、錯誤型別或未成功取得明細不使用零值補齊。`active` 且到期欄位無效的單筆仍按既定資格規則處理，不讓其他欄位成功掩蓋整個查詢失敗。

本功能不更新 OAuth token、不呼叫 CLI 代為登入。Codex 來源可讀但 API 回報未授權時，不因 401 靜默切換其他帳號；記錄登入失效，暫停同一失效憑證的定時請求，憑證更新或程序啟動後才重新檢查。解析器來源優先順序維持既有慣例；任何來源變更仍須重新核對帳號範圍。

持久化的 `account_scope` 為 provider 與 ChatGPT 帳號 ID 組成的穩定雜湊，不使用 access token 或憑證路徑作身分。缺少可驗證帳號 ID 時可保留既有唯讀顯示，但禁止消耗。帳號切換取消舊候選工作、清除僅依 provider 建立的自動化暫存，重新查新帳號。舊帳號的歷史紀錄不刪除，也不顯示成新帳號的結果。

Codex snapshot 增加選填的 `accountScope`，非 Codex provider 不受影響；內部查詢另捕捉設定／帳號世代。舊快照或未確認目前帳號的快照僅可唯讀，不能授權手動消耗。App 開啟確認視窗時捕捉所見快照的 scope，consume IPC 除 `requestId` 外必須帶 `expectedAccountScope`；後端以此與目前解析結果比對，不能把呼叫端 scope 當成憑證。確認期間切換帳號即取消本次操作並刷新，不靜默改用新帳號。

沿用 provider-key 快取，但所有 Codex writer 在提交記憶體／DB 前核對 scope 及世代；核對與發布須協調為同一短臨界區，不能在核對後再允許切換穿插並覆寫。不符則丟棄過期結果，不需要為本次功能改造所有 provider 的多帳號資料結構。重啟載入的持久 Codex 快照先標示未確認，成功核對目前登入帳號後才可操作。`quota-snapshots-updated` 可維持既有 invalidate 事件，前提是舊帳號結果不能寫入目前快取；自動化狀態事件攜帶 scope／世代供 App 丟棄過期回應。舊帳號消耗回應仍完成自己的日誌，不得刷新覆寫新帳號資料。

手動與自動均進入 quota 內部的同帳號消耗協調器，先取得執行權，再重查資料、寫入請求紀錄、POST、記錄結果並刷新。使用執行中的帳號鎖及資料庫唯一條件避免不同觸發來源重複執行；不得持有全域 DB／快取 mutex 等待網路回應。若有另一筆請求進行中，手動路徑可回報處理中，自動路徑留待下輪重新評估。

Dashboard 手動操作保留既有「全域用量監控與 Codex 用量 provider 開啟」的條件；不因停用 Codex session 掃描而禁止手動使用。重置券提醒及自動使用則不依賴上述平台開關，只依自身旗標、帳號與原有券資格檢查。

手動新消耗亦須確認 active 明細數與可用數一致，不能只因總數大於零就使用。核對 unknown 時，未知狀態不得視為已不可用；若目前明細不完整／計數不一致，亦不得單憑原券未出現在清單就解除阻擋。憑證拒絕的記憶以獨立的憑證指紋辨識，POST 401／403 與 GET 共用；指紋不含設定世代，避免不相關的設定保存重新啟用同一失效 token。

**取捨：** 重用現有 API 與 UI 確認流程，不由背景協調器呼叫 Tauri command，也不新增自動模式繞過共用協調。

### 4. 以到期批次處理多張券，不偽造逐券識別

自動批次以 `(account_scope, expires_at_utc)` 識別，同效期相同明細以張數保留，不以內容去重而遺失張數。首筆請求前保存該批次可用數作為本批次上限；批次已有終止紀錄時，不因刷新、重啟或不同設定版本重新產生批次。

目前沒有已驗證的選券契約，因此首版僅允許：

- 只有一張可用券，且該券已進入到期區間。
- 所有可用券均有相同且已知的到期時間，且已進入到期區間。

若未來能以可核對的服務端契約證明最早到期優先，再放寬混合效期；本次不得從回傳排序或單次觀察推論。任何 active 券缺到期時間、混合效期或明細／總數不一致，均顯示對應暫停原因，不盲目消耗較晚到期券。

允許的批次逐次 POST，`reset` 後必須重新查詢，確認該批次張數減少且仍未到期，才繼續。總請求數受最初到期張數限制；`nothing_to_reset`、`no_credit`、`already_redeemed`、錯誤、結果不明或無法確認張數減少皆終止本批次，不在下一個 tick 重新開始。`nothing_to_reset` 只表示此次無需重置，不推論所有剩餘券已使用。

**取捨：** 無法保證所有券都能使用，尤其服務端沒有需要重置的用量時；保留這個實際結果比反覆 POST 或假造成功更符合 API 能力。

### 5. SQLite 保存提醒去重與消耗日誌

在現有 `metadata.db` 進行加法式 migration，業務 helper 置於 `db.rs`／既有 DB 分工：

| 紀錄 | 唯一範圍 | 必要內容 |
| --- | --- | --- |
| `reset_credit_reminder_checks` | `account_scope + local_date` | 檢查狀態、GET 次數與進行中標記、下次可嘗試時間、今日／未來張數、檢查與通知提交時間、錯誤分類 |
| `reset_credit_auto_batches` | `account_scope + expires_at` | 初始張數、GET 次數與下次可嘗試時間、已嘗試序號、批次狀態、停止原因 |
| `reset_credit_consume_attempts` | `request_id`；自動來源另限 `batch + ordinal` 唯一 | manual／automatic 來源、帳號、觀察到的到期批次、送出前時間、狀態、API 結果、更新時間 |
| `reset_credit_query_backoff` | `account_scope + endpoint` | 服務端要求的下次可查詢時間，讓重啟及不同觸發來源共同遵守 |
| `reset_credit_preferences` | `key` | 保存目前通知語系；由 App 同步已儲存的 zh-TW／en-US 偏好，不新增使用者設定開關 |

提醒成功查到零張時寫 `checked_empty`，當天不再重查提醒。通知前先原子保留當日的 `claimed` 紀錄，再呼叫通知；提交後寫 `dispatched` 或 `failed`。通知 API 只能證明提交，不能證明顯示或已讀；崩潰留下的 `claimed` 不再自動重送，採至多一次提交。GET 失敗尚未進入通知保留階段，可依有界策略重試；耗盡後記錄當日檢查失敗。當日修改提醒時間／提前天數不清除已檢查紀錄。

消耗送出前先保存 request ID 與 `pending`，確保不能在沒有可寫日誌時消耗。回應已知時寫結果；逾時、連線中斷、未知格式或重啟遺留的 `pending` 轉 `unknown`。不假定 `redeem_request_id` 具足以安全重送的服務端冪等保證，因此不重送同 ID，也不換新 ID 自動重送。

request ID 一旦存在即不可改變其帳號／來源／操作內容。相同請求再次抵達只讀回既有狀態；不同內容則拒絕，不能用 upsert 覆寫後重新 POST。缺少 request ID 或 expected scope 在進入送出階段前拒絕。自動化不透過前端產生消耗 ID。

`unknown` 存在時暫停該帳號後續消耗，重新查詢以對照原先觀察的到期批次。原批次已不存在可用券或全部到期後解除阻擋，但歷史仍保留結果不明，不改標成功。手動不指定券，故其不明紀錄須包含請求前所有可用批次，不能只猜最早一批；無到期資訊的原券仍存在時持續保留阻擋。

若 DB 無法寫入、已存在無法排除的 pending／unknown，或刷新不能核對帳號，禁止新的消耗。只存分類及必要到期資訊，不存 token、授權 header 或原始憑證。

以上表是操作日誌，與 quota snapshot 的 prune／重建分離。停用 provider、關閉開關及清除可重建快照均不得刪除此日誌；歷史沿用 metadata.db 的生命週期，不新增自動清理策略。保證範圍是同一份完整的資料庫；外部刪除、替換或回復舊備份後無法還原已遺失的去重證據，本次不新增偵測外部還原或第二份影子日誌機制。DB 執行中失效時停止副作用，不以清空表格自動修復。未來若提供資料重設／備份還原功能，須另定此操作日誌的處理契約。

**取捨：** 採持久化「至多一次發送＋可觀察不確定結果」，不宣稱不可能保證的端到端 exactly-once。

### 6. 設定與狀態使用既有 UI 模式

在 SettingsView 新增與 quota card 同層的獨立重置券 card，使用既有 switch、時間與數字輸入及 `sessionhub-minimal-ui` 設計語言。子元件接收 props；儲存、初次狀態讀取與事件訂閱集中於 App。

新增唯讀自動化狀態 IPC，由 App 取得／訂閱後傳給設定頁，內容包括目前帳號的提醒／自動使用有效狀態、原因代碼、下一次提醒檢查時間、最近一次嘗試時間與結果。不將 token 或原始帳號 ID 傳到通知文案。原因及結果以穩定代碼傳遞，前端與 Rust 通知依目前已儲存語系產生文案。

狀態區區分 `disabled`、`ready`、`paused`、`running`，結果區分 `reset`、`nothing_to_reset`、`no_credit`、`already_redeemed`、`failed`、`unknown`、`missed`。消耗完成後重新整理 Codex 快照並發事件，沿用現有刷新管線更新 Dashboard、狀態列及其他用量顯示。

狀態以 `reminderReason` 與 `autoUseReason` 分別說明；錯誤 fallback 依最新已儲存開關維持 disabled，不能一律將兩個功能設成 paused。前端在 await 查詢完成後才與最新事件快取比對世代，避免較舊查詢覆寫新的狀態；沒有帳號的錯誤狀態可顯示原因，不當成其他帳號資料。

設定讀取／保存、終端驗證、快照身分核對及 watcher 重啟以 async command 加 spawn_blocking 執行。設定 command 的保存與後置效果以獨立 worker 鎖序列化，不持有設定寫入閘門等待原生視窗工作。只在對應欄位變更時同步 autostart、清理 quota 或更新 tray／overlay；前端只在來源／平台變更時重啟 watcher，只在工具路徑變更時重新偵測工具。保存成功即更新 settings 快取，不 await 無關重載。背景讀取使用不探查平台授權的輕量 loader；設定檔以同目錄、程序專用暫存檔 rename 取代，避免非同步讀取看見半寫入 JSON。

原生到期提醒僅受提醒開關控制；自動使用結果保留在設定狀態及既有應用程式回饋，不額外引入獨立「結果通知」開關或通知中心。通知權限僅影響提醒。沿用 SessionHub 正式通知 identity，以安裝版驗證；使用者沒有權限或 OS 不顯示時，狀態清楚說明，不阻斷自動使用。

`ready` 表示已啟用且具備預定執行資格，尚未進入一分鐘區間不是暫停原因；`running` 才表示已取得送出執行權。提醒文案依通知當下的資格判斷，不預測未來登入／網路狀態。`unknown` 提供重新整理核對動作；登入失效提示在原工具重新登入；選券限制提示手動處理。若未知結果仍未釐清，不能以手動處理提示繞過帳號級阻擋。下一次提醒時間在關閉、前置條件未成立或無法確認帳號時為空，並顯示原因；當日已檢查則顯示下一日設定時間。

### 7. 明確定義消耗傳輸與狀態轉移

目前 Cargo.lock 鎖定 ureq 3.5.0；文件顯示無內建自動 retry，但預設會跟隨 redirect。重置券 GET／POST 均顯式傳入最多 10 秒的整體 timeout，涵蓋回應本文讀取；consume 的 request-scoped 設定禁用 redirect（`max_redirects(0)`），不改全域其他 provider 政策。使用隔離 HTTP server 驗證實際鎖定版本對 3xx、逾時與連線中斷不重送 POST。

| 階段／結果 | 狀態與後續行為 |
| --- | --- |
| 等待期限、帳號鎖、GET 或前置條件 | 尚未取得送出執行權，可取消；暫時性 GET 依持久化預算重試 |
| 最後核對成功並取得送出執行權 | 先寫 pending，再發一次 POST；已進入副作用執行階段 |
| 明確 reset／nothing_to_reset／no_credit／already_redeemed | 保存原結果；只有 reset 且重查同批次減少才可續下一張 |
| 本地送出前可確認失敗，或明確的 401／403／429 拒絕回應 | 保存 failed 及原因，停止本批次；401／403 顯示登入原因，429 保存退避，不另發 consume |
| POST 逾時、I/O 中斷、3xx、不明 5xx、解析失敗、重啟遺留 pending | 保存 unknown，帳號級阻擋；不因傳輸錯誤推論未消耗 |
| API 結果已知，但後續日誌寫入失敗 | 不發後續 POST；記憶體保留已知結果，持久 pending 在重啟後保守視為 unknown |

若無法從函式庫錯誤證明尚未進入送出階段，一律採 unknown。重新查詢只能證明原觀察券是否仍可用，不足以把 unknown 升級為本請求 reset；歷史成功只能來自明確 API 結果。

## Risks / Trade-offs

- **一分鐘區間短且有網路延遲** → 十秒檢查、事前發現候選、請求逾時及到期前重查；超過期限不補用，明確呈現失敗／錯過。
- **無指定券與選券順序契約** → 首版採單張或全數同效期的可確認範圍，混合效期提供暫停原因，不能宣稱必用掉特定券。
- **程序退出、休眠與關機** → 生命週期補查僅針對仍有效工作，設定頁說明執行範圍；不自動修改開機啟動或最小化至系統匣設定。
- **至多一次通知可能在崩潰時漏送** → 接受比重複提醒更小的副作用，保留提交狀態供檢查。
- **API 成功與 DB 更新無法形成跨系統交易** → 預先日誌及 unknown 狀態，不盲目重送；同一帳號手動與自動都遵守阻擋。
- **既有 quota 查詢為 best-effort，null 不等於零券** → 自動化使用有明確成功／失敗分類的直接查詢，保留既有 Dashboard best-effort 行為。
- **操作日誌被外部刪除或回復舊版** → 無法保證跨資料庫替換的去重；本次將此列為保證邊界，維持日誌不受日常快取清理影響。

## Migration Plan

1. 新增設定預設及逐欄位驗證，缺新欄位的舊設定載入後兩個開關皆關閉。
2. 新增 SQLite 表與唯一條件，不刪除既有快照／session 資料；Codex 舊快照缺帳號範圍時標為未確認，不直接授權消耗。
3. 先接妥共用帳號及手動消耗協調，再啟動提醒／自動批次；背景功能只有在已儲存設定開啟時運作。
4. 以隔離資料目錄、假時鐘／假 HTTP 完成自動驗收；原生通知以 Windows 安裝版驗收，測試不得實際消耗真實帳號的券。
5. 回復時先關閉兩項開關並確認沒有執行中請求。可保留新增表及設定欄位；回復到不認識日誌的舊版本時，不重播未完成工作，舊版手動操作無法提供新版本的不明結果阻擋保證。
